# 分块精确增量召回（2026-10-04）

## 内存范围

精确成员矩阵缓存的默认保留上限为 32 MiB。增量召回会在构建完整矩阵前按
`len(member_ids) * (query.width * 8 + 64) + 256` 估算成本；超过 32 MiB 时直接转入
分块扫描，不构建完整矩阵。缓存容量按估算成本计：
`matrix.nbytes + 64 × member_count + 256`，包含矩阵载荷和保守的逐成员对象开销。
通用 `RequestLocalMemberMatrixCache.get` 对超限矩阵的行为是加载完整矩阵供本次调用
使用、但不放入 request-local LRU；这不是增量召回的超限路径。小矩阵即使因 LRU 容量
压力被逐出，仍走普通完整矩阵路径；仅因逐出不会触发分块扫描。32 MiB 上限约束缓存
保留量，不是单次矩阵构建、分块 scratch 或进程 RSS 上限。

未能缓存的大成员集合走分块精确扫描。默认最多 256 行，scratch 预算为 4 MiB；
每行按 Float64 计，并保守估算三份矩阵工作区（行组装、归一化和评分）。若 embedding
宽度为 512，估算行数为 256 × 512 × 8 × 3 = 3 MiB，故默认行数限制先于 4 MiB
预算生效。容量计算等价于
`min(256, max(1, 4 MiB // (width × 8 × 3)))`。即使单行的三矩阵估算已超过预算，
至少仍扫描一行以保证前进；此时 4 MiB 不是硬性的瞬时内存或总 RSS 上界。

## 数值与选择语义

分块扫描按固定的逐行 `einsum("ij,j->i", ..., optimize=False)` 计算归一化向量
余弦分数，不随 chunk batch 形状改变归约方式。缓存矩阵路径仍使用现有矩阵乘法。
不同 Float64 归约（例如逐行 einsum 与 BLAS 矩阵乘法）对数学上相同的分数可能相差
一个或数个 ULP；代码不会把容差内的近似值人为压成平分。分块选择使用严格 `>`：
分数完全相同才保留较早的成员，哪怕后一个成员仅高一个可表示浮点数也仍可胜出。

两条评分路径共用分数校验：拒绝非有限值或越出单位余弦范围的结果，仅裁剪允许的
端点舍入误差。扫描不会在找到暂定赢家后提前退出；每个后续 chunk 仍会完成归一化和
全行分数校验，因此无效的非赢家也会失败。缺失成员按既有语义跳过；存在的成员仍需
通过 fingerprint ID、向量形状、有限值和分数检查。

套件为 1775 passed、47 warnings，仅忽略尚未完成的
