# riskfolio_qs 下一阶段总纲 v0.2

## 1. 项目交付形态

最终交付形态定义为：

1. 用户从 CLI 或 Python 主入口启动。
2. 只需要提供一个配置文件路径。
3. 系统根据配置自动完成数据加载、优化器装配、求解、结果落盘。
4. 输出目标仓位文件到指定目录。

一句话目标：配置驱动的一键组合优化执行器。

## 2. 期望使用形态

### 2.1 外围调用方式

方式 A：CLI

python -m riskfolio_qs --config /path/to/config.yaml

方式 B：Python 主入口

from riskfolio_qs.runners.run import run_from_config
run_from_config("/path/to/config.yaml")

### 2.2 必须产物

1. 目标仓位宽表（date x asset）。
2. 调仓表（可选但建议默认输出）。
3. 组合摘要表（换手、净敞口、总敞口等）。
4. 审计元数据表（模型、参数快照、求解器、状态）。
5. 运行日志（配置摘要、阶段耗时、异常信息）。

### 2.3 成功标准

1. 同一配置在同一数据下可复现。
2. 不修改源码即可切换策略模式和参数。
3. 可用预置模式快速跑，也可细粒度配置跑。
4. 当 Riskfolio 原生接口缺少硬约束时，可在 vendor 内核扩展并保持外层参数化调用不变。

## 3. 配置内容约束

### 3.1 配置接口模式

配置需要支持两种入口：

1. 合约模式（Preset Contract）。
2. 目标函数模式（Objective Config）。

二者底层走同一优化器装配流程，差异只在参数来源。

### 3.2 输入数据约束

配置文件中必须能描述输入数据路径，支持两种方式：

1. explicit：逐项指定 alpha、market、risk_factor、industry、benchmark、prev_positions 等文件路径。
2. folder：只指定一个目录，由固定目录结构解析数据文件。

### 3.3 优化器配置约束

配置需要支持：

1. 预置策略名，如 minvar_enhance_index。
2. 目标函数类型，如 mean_variance。
3. 硬约束参数。
4. 目标函数内部参数。
5. 求解器名称与选项。

### 3.4 内核扩展原则

1. 外层配置协议保持稳定。
2. 若原生接口没有目标硬约束，允许在 vendor/riskfolio 中做最小可追踪扩展。
3. 所有扩展约束必须进入统一约束注册表。
4. vendor 变更必须有差异清单和回归测试。

## 4. 配置示意

建议主格式使用 YAML，配置应至少覆盖 run、input、optimizer、solver、validation、logging 六部分。

重点不是具体字段固定到一行不差，而是保证：

1. 输入路径可表达。
2. 预置策略可表达。
3. 目标函数可表达。
4. 硬约束可表达。
5. 内核扩展约束可表达。

## 5. 结论

这套设计的本质是：

1. 统一配置契约。
2. 双颗粒度入口（预置策略名 / 目标函数参数化）。
3. 单执行主入口（CLI 或 run.py）。
4. 标准结果输出到指定路径。
5. 内核可扩展约束，但外层始终参数化调用。
