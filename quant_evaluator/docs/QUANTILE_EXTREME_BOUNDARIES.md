# 分层边界极值修复与冷启动定位（2026-09-22）

## 为什么影响自动优化

优化器的成本后多空组合与分层诊断都依赖 QE 分位分组。
即使因子输入都是有限数，相邻排序值的差也可能溢出：
[-1e308, 1e308] 的二分位边界应为 0，旧公式却生成 inf，
导致多空两端被错误合并。这是分层计算错误，不是因子本身无效。

float32 相减溢出和 int64 相减回绕也可产生错误边界。
修复前 20 个 CPU/JIT 路径反例失败；修复后通过。
另有 GPU 数组算法的 2 个相同反例已复现并修复。
二十分层的极值平台、min/max 并列策略另有手工预期测试。

## 计算口径

排序后相邻值为 l、r，插值比例 f：

$$b=l+f(r-l)$$

保留原有接近整数位置（1e-9）的端点吸附及 min/max 并列策略。
相减前转为 float64，避免窄浮点和整数运算溢出。
若差值在 float64 中仍不可表示，则使用等价的凸组合：

$$b=(1-f)l+fr$$

仅无法安全相减的分支改用凸组合；正常 float64 数据保持原运算顺序。
GPU 吸附端点单独选取原端点，避免 0×inf 导致 NaN。
这不是对因子做缩尾或截断，原始因子值不变。

## 验证边界

CPU 参考、fast、batch、JIT 入口与 GPU 数组实现均覆盖。
GPU 数组测试以 NumPy 执行真实数组算法，仅证明算法层行为，
不替代 CUDA 设备、驱动或显存验收。真实收益不因此获得保证。

专项测试最终 24 项通过；FO+FP 完整回归 1813 passed、1 xfailed，
后者是已限制为 OFFLINE_ONLY 的 HP 非因果性案例。
QE 更新指标参考文档后完整复验 1310 passed、2 skipped、10 warnings。
两项跳过是 build/lib 尚无对应标准化/删行内核的契约测试。
平台根测试仍为 14 项收集错误（1 skipped、2 warnings），模块清单见
../../factor_optimizer/docs/METHOD_AUDIT_20260922.md；没有宣称全平台通过。

## 真实 A/B

通过 DataAccess 读取绑定因子 weekly_db5616cd85a477b3，500 日×256 股票，
103 候选，99 次自助抽样。热身后按 old/new/new/old/old/new 交错运行；
旧函数从已提交源代码提取到内存，没有复制仓库或更换数据集。
六次的输出数组、全部候选记录、选择身份和验证下界逐项一致。
TEST 未评分，内容 SHA256 见 quantile_extreme_real_ab_20260922.json。

旧实现中位 15.0574 秒，新实现 15.4416 秒（约 +2.6%）。
这次是正确性修复，不据此声称提速；运行噪声及并行任务存在，
三组不足以证明显著性能差异。冷启动改善需另作独立对照。

三库合并收集时发现同名 test_review_regressions 模块冲突，
涉及 quant_evaluator/tests 和 factor_preprocess/tests/transforms；
因此完整回归分为 QE 与 FO+FP 两次运行，不宣称合并运行通过。
平台根测试的既有收集问题也另行记录，不屏蔽检查。

## 冷启动证据与后续重点

对清单绑定的 weekly_db5616cd85a477b3（500 日×256 股票）执行一次 cProfile：
整体 optimize_factor_batch 累计约 83.77 秒，其中 FE 注册表/算子初始化约
61.01 秒，首次 ensure_cleaned_loaded 约 59.76 秒。
这是带 profiler 的冷启动观测，不是无插桩性能承诺。

当前 FP 的权威 FE 算子适配器首次调用会加载完整算子注册表。
这解释了只改评分循环不能解决首次使用慢的问题。
后续应分别验证冷启动加载与热运行的性能；不能为提速绕开算子权威、
因果性检查或生产准入，也不能覆盖其他 AI 正在修改的 FE 注册表代码。
