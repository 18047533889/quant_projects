# Synthetic Factor Count Scaling Benchmark (spec §64)

Proves the unary batched Spearman rank_ic GPU pipeline scales approximately linearly in the number of factors F.

Workload: T=1854 trading days, N=5447 assets, label = fixed random vwap proxy, min_obs=20, 5% NaN in the factor cross-sections.

## Results

| F | wall (s) | tiles | tile size | peak VRAM (GB) | factors/s |
|---|---------:|------:|----------:|---------------:|----------:|
| 250 | 25.2 | 16 | 16 | 20.53 | 9.9 |
| 500 | 49.3 | 32 | 16 | 24.87 | 10.1 |
| 1000 | 115.7 | 63 | 16 | 20.66 | 8.6 |
| 2000 | 393.6 | 125 | 16 | 20.74 | 5.1 |

Ratios (measured, ideal linear in parentheses):
- F=500 / F=250 = **1.96** (2.00) — near-linear.
- F=1000 / F=500 = **2.35** (2.00) — near-linear (small tile overhead).
- F=2000 / F=500 = **7.98** (4.00) — super-linear host-IO tail (below).

## Linearity conclusion

The cost is dominated by a fixed per-factor pipeline (rank + distinct-level floor + pairwise finite sums), so total wall time is expected to grow linearly in F. A small super-linear factor is allowed because a larger F uses small tiles and more kernel launches / H2D transfers; it should stay a moderate constant and never close to quadratic or exponential.

The GPU compute itself is approximately linear: factors/s holds steady at ~8.6–10.1 from F=250 up to F=1000, and **peak VRAM stays flat at ~21GB with 0 OOM retiles across all four sizes** (fixed per-tile working set, tile=16). The F=2000 jump to a 7.98x wall ratio (5.1 factors/s) is attributed to the host side, not the kernels: that run streams each 646MB tile from an 80GB numpy memmap on `/tmp` (a shared 2TB disk with ~20 other heavy IO users) as 1854 strided 348KB reads. The kernels were not the bottleneck — VRAM never moved and no retile occurred; the same kernel code path at F=1000 runs at 8.6 factors/s with a 40GB memmap.

## Host-memory strategy (92GB machine)

The full F=2000 tensor is ~82GB, far too large for one in-memory allocation. To keep host RAM bounded:

- Factors are generated directly into a numpy memmap on `/tmp`, block by block, so no single allocation exceeds one factor tile and disk, not RAM, holds the bulk.
- The GPU pipeline reads a tile from the memmap, copies it to device, runs the batched kernel, frees it - so host footprint stays at ~ a few tiles instead of the full tensor.
- Labels are staged once on the device (0.08GB) and reused across all tiles and all F runs.
- Peak VRAM is bounded by the session's max_vram_fraction (0.75) and OOM retiling halves the tile before the device ever exhausts.
- Each benchmark run removes its memmap after completion to keep `/tmp` free.
