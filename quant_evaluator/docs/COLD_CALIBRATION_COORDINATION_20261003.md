# 精确批次校准：冷请求协调（2026-10-03）

## 为什么需要协调

同一个进程内，两条并发的冷校准可能同时运行 CPU/GPU，对方的负载会
污染计时。缓存的线程安全并不等于计时实验是串行的。

`runtime/calibration_measurement_coordinator.py` 维护一个进程级锁，
不存储请求键、不调整线程数量、不控制其他应用的任务。它只串行化
本进程的冷校准实验；不能保证服务器其他业务静止或未来仍然最快。

## 接入与执行顺序

公开 `evaluate_calibrated_batch` 的签名不变：先检查输入、身份、缓存
及设备准入。已有合格缓存或设备不支持 CUDA 时，不请求计时锁。
只有冷缺失进入协调器；得到 reservation 后重新计算完整请求、源码、
运行时和设备身份，并重新检查缓存。等待者因此可以直接使用首个实验
刚写入的合格缓存，不会用等待前的旧身份提交新的计时记录。

返回元数据 `calibration_queue_seconds` 记录等待 reservation 的时间。
等待计入原请求软预算，剩余预算约束锁等待；正在执行的公开评估不能
安全强制中断，原有“在两次后端调用之间检查预算”的行为仍然适用。
操作系统锁的可表示超时使用 `threading.TIMEOUT_MAX` 截断，避免合法的
巨大有限预算触发系统 `OverflowError`，不是改变用户校准预算字段。

预算约束的是冷校准测量，不是整个请求的硬截止时间。初次缓存命中、
或者排队后重新验证身份时命中合格缓存，仍执行一次已选后端的推理；
即使此前身份检查或排队已消耗软预算，也不会强制中断这次缓存推理。
排队后仍未命中缓存时，首个冷测量调用之前检查原请求预算，耗尽则拒绝。

同线程嵌套计时立即拒绝，避免死锁；异常退出释放锁。fork 子进程通过
at-fork 回调以及 PID 防护重建锁和线程局部状态，不继承父进程的锁等待。
这是进程内协调，不是多进程或整台服务器的调度器。

## 验证与默认 auto 的边界

事件控制的并发测试验证：相同键只有一次四调用校准及一次缓存推理；
等待后身份变化使用新键、设备准入丢失回到 CPU；缓存命中在锁已占用时
仍可正常执行。独立测试覆盖异常、重入、超时及持锁 fork。

这次修复不把每个新输入改成默认六次冷评估。显式 `auto_calibration`
仍负责填充精确校准缓存；默认 `auto` 仅复用通过其身份与资格检查的
记录。静态形状选路不等于当前源码、当前线程配置下已实测的最快后端。
