# Factor Evaluation AlphaPurify Development Prompt

以下内容可直接作为后续 AI 协作 prompt 或开发约束说明，目标是让这个库长期保持单一正式主流程，同时保留可运行的历史内核用于一致性验证。

## Prompt

你正在维护一个因子评估库。这个库的目标不是同时维护多条公开主流程，而是在外部只暴露一套正式、稳定、最新的主流程，同时在内部保留可运行的历史模块，用于验证重构前后是否只是代码结构变化，而输入输出语义保持一致。

这个库的结构遵循以下原则。

第一，包根目录只保留正式运行层。根目录中的模块代表当前默认、最新、正式支持的实现，包括预处理模块、工具函数、配置模块、数据适配模块、暴露分析模块、因子分析模块、流程编排模块、配置入口和命令行入口。外部调用方只应该理解一条调用链：命令行入口 -> 配置入口 -> 正式 pipeline -> 标准输出。

第二，历史版本不再作为第二套公开主流程存在，而是放入一个独立的历史模块目录。这个目录存放可切换运行的版本内核，既包括历史快照，也包括开发过程中的候选版本，例如某一版 Exposures、某一版 FactorAnalyzer、某一版 Database。历史模块的作用是回归验证、行为对照和受控开发，而不是成为新的公开入口。历史模块文件命名应该清晰表达模块名和版本信息，例如按模块名加日期或版本号命名。

第三，参考代码、上游快照、一次性实验脚本和旧的 pipeline 试验文件，不属于正式运行层，也不属于历史内核层，而应当放入归档层。归档层仅用于追溯和参考，不参与正式运行逻辑。

第四，外部永远只保留一条主流程。不要新增第二个正式 pipeline，不要新增第二个正式 run 入口，不要通过 new、old、test、temp 这类并列文件长期承载正式逻辑。所有新开发都应当优先融入正式主流程。

第五，模块版本切换必须集中管理。是否使用正式 Exposures、历史 Exposures，或其他历史 FactorAnalyzer，不应当散落在多个流程步骤里判断，而应当由一个集中选择层统一解析，然后把最终选中的内核注入正式 pipeline。正式 pipeline 只负责编排，不负责维护多套分支逻辑。

第六，pipeline 和 module_selector 在默认情况下必须优先选择根目录中的正式模块。只有开发者在开发、回归验证或定向对照时显式指定某个版本，才允许切换到历史模块目录中的对应实现。根目录始终是当前正式版本的唯一默认真源，历史模块目录中的副本即使与根目录内容相同，也不自动替代默认行为。

第七，开发某个核心模块时，推荐采用版本化开发工作流。开发者修改模块前，应先将根目录中的当前正式模块复制到历史模块目录，并按日期和版本号重命名，再基于该副本进行开发与验证。例如在 5 月 5 日开发 Exposures 的 v1.2，可先复制 Exposures.py 到历史模块目录并命名为 Exposures_0505_v1.2.py，再通过 pipeline 和 module_selector 显式选择该版本完成运行验证。

第八，历史模块必须遵守统一的输入输出契约。无论是当前正式模块还是历史模块，只要被正式 pipeline 调用，就必须接受同一份标准化输入，并返回同一语义层级的输出结果。验证重构是否只是结构变化时，比较的是同一输入下的结果一致性，而不是比较两套各自定义的流程。

第九，正式开发优先保持外壳稳定，内核可演进。也就是说，配置入口、命令行入口、主流程编排、输出目录结构和结果摘要格式应尽量稳定；真正允许演进和替换的是内部分析内核，例如 Exposures 和 FactorAnalyzer。

第十，后续新增重构版本时，默认流程应是：先在历史模块层新增一个可运行版本，用统一输入完成对照验证；如果确认只是结构优化且行为符合预期，再把它提升为根目录中的正式最新实现；被替换下来的旧正式实现再下沉到历史模块层。这样可以保证外部始终只有一套最新接口，内部又保留完整回归能力。历史模块目录中保留的最新版副本可以与当前主模块内容一致，但它的角色仍然是版本快照和开发记录，而不是默认正式入口。

第十一，比较模式和生产模式要区分。生产模式是选择一套内核正常运行并输出结果；比较模式是在同一份标准输入上运行正式模块和历史模块，并对核心结果进行一致性检查。比较模式是验证工具，不应污染正式生产流程。

第十二，所有后续开发都应遵循以下判断顺序。

1. 先判断需求属于正式流程增强、历史模块验证，还是归档参考整理。
2. 如果是正式能力增强，优先改正式模块。
3. 如果是历史一致性验证，优先接入历史模块而不是复制整条流程。
4. 如果只是草稿、实验或上游对照资料，放入归档层，不进入正式运行链路。

你的工作目标不是让这个库同时存在多套看起来都能跑的流程，而是让它形成“一套正式主流程 + 一组可切换历史内核 + 一层归档参考”的清晰结构。任何代码调整、重构、文档补充和新模块接入，都应服务于这个结构。

## Suggested Package Shape

建议长期收敛到如下目录边界：

- 根目录：正式运行层，只保留当前正式模块。
- history_module/：版本内核层，保存可切换运行的历史快照和候选开发版本。
- archive/：归档参考层，存放上游快照、实验脚本和废弃过渡文件。

建议的正式调用链如下：

run.py
-> run_from_config.py
-> pipeline.py
-> module_selector.py
-> selected Database / Exposures / FactorAnalyzer
-> output writer

在这个结构下：

- run.py 和 run_from_config.py 只作为正式入口。
- pipeline.py 只作为唯一正式编排层。
- module_selector.py 负责根据配置解析要用哪一版内核，默认选择根目录正式模块，只有显式指定版本时才切换到 history_module。
- Database.py、Exposures.py、FactorAnalyzer.py 代表当前正式实现。
- history_module 中的版本脚本只在开发、回归对照或显式版本验证时被选择使用。

## Development Rules

后续开发时，默认遵守以下规则：

1. 根目录永远只保留当前正式版本，不保留 old、new、temp 这类长期并存文件。
2. history_module 中的版本文件不作为默认公开入口暴露，只有显式指定版本时才运行。
3. 实验性质的 pipeline、一次性对比脚本和上游源码快照，只能进入 archive，不进入正式链路。
4. 任何重构都应优先保持输入输出契约稳定，再考虑代码结构优化。
5. 如果需要验证重构前后是否等价，应使用同一份标准输入分别调用正式模块和历史模块，再对核心结果做一致性比较。
6. 开发某个核心模块前，应先将根目录中的当前正式模块复制到 history_module，并按日期和版本号命名，再基于该副本进行开发与验证。
7. 候选版本验证通过后，可晋升替换根目录中的正式模块，而其在 history_module 中的副本继续保留，作为版本快照和开发记录。
