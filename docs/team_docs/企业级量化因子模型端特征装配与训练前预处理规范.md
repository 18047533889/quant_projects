# 企业级量化因子模型端特征装配与训练前预处理规范

面向模型组、特征平台组、MLOps 组和需要实现 `Feature Store / Model Training / Online Serving` 的工程团队。

## 0. 文档定位

这份文档是从主需求文档中拆出来的模型端专用规格。它解决的是下面这些问题：

- 因子评估与入库完成后，哪些对象允许进入模型端
- 模型端如何做 `PIT` 安全特征读取
- 横截面与时序因子分别如何预处理
- 树模型、神经网络、序列模型分别吃什么形态的输入
- 如何避免 `training-serving skew`
- 如何管理 `Feature Store`、特征新鲜度、血缘和线上线下一致性

如果只看主需求文档，模型组能知道流程边界；如果要真正写模型端代码，应以本文件为准。

## 1. 与主需求文档的边界

主需求文档负责说明：

- 因子从候选到评估、贴标、路由、入库的主线
- 因子评估基建组需要提供给模型端的对象、文件和接口
- 模型端在总链路中的位置

本文件负责说明：

- 模型端如何消费这些对象
- 如何落地训练前预处理
- 如何组织 `Feature Store`
- 如何实施验证、上线和审计

一句话：

- 主文档管“因子怎么进入模型端”
- 本文档管“模型端拿到因子以后怎么安全地变成可训练特征”

## 2. 输入边界与准入规则

### 2.1 允许进入模型端的来源

默认只允许以下来源进入模型端：

- `Tier 3A`
- `Tier 3B`
- `Tier 3C`
- `Tier 3D`

不允许直接进入模型端的来源：

- `Tier 0`
- `Tier 1`
- `Tier 2`
- `Tier 2X`
- `Tier 4`

原因：

- 这些层级要么尚未完成评估与治理，要么是中间加工态，要么是明确失败对象

### 2.2 入模最小条件

进入模型端的每个因子必须至少满足：

- 已明确 `library_key`
- 已通过 `PIT` 安全审计
- 已有标准评估产物和评分卡
- 已有标签与血缘
- 已有最近一次可复现的评估配置快照
- 已有 `feature_store_allowed` 标志

### 2.3 必填字段

模型端读取时，至少要求每个因子带以下字段：

- `factor_id`
- `library_key`
- `signal_structure`
- `asset_class`
- `frequency_bucket`
- `domain_root`
- `knowledge_ts_policy`
- `feature_store_allowed`
- `online_serving_allowed`
- `current_tier`
- `current_state`
- `source_factor_id`
- `optimization_batch_id`

## 3. Point-In-Time 安全规范

### 3.1 核心原则

任何训练样本在时间点 `t` 上使用的特征，必须是 `t` 时刻已知或之前已知的信息。

因此必须满足：

- `knowledge_ts <= decision_ts`
- 标签计算区间不能回流进特征构造
- 训练集、验证集、测试集之间不能发生时间重叠污染

### 3.2 必须保留的时间字段

- `event_ts`
- `knowledge_ts`
- `decision_ts`
- `label_start_ts`
- `label_end_ts`

### 3.3 点时查询要求

模型端训练集构造必须采用 `as-of join / point-in-time join` 语义：

- 主键按 `entity_key`
- 时间键按 `decision_ts`
- 取该时刻之前最近一次已知特征值
- 不允许取 `decision_ts` 之后才出现的值

### 3.4 典型错误

以下做法视为硬错误：

- 使用当前最新特征回填整个历史训练集
- 使用未来修订后的基本面值覆盖历史已知值
- 对全样本一次性拟合 `scaler` 后再切训练集和测试集
- 用未来窗口统计量构造当前特征

## 4. 数据切分与验证规范

### 4.1 默认验证方案

默认推荐：

- 日频横截面因子：`walk-forward` 或 `rolling window`
- 高频或序列模型：`walk-forward + rolling window`

### 4.2 必须支持的验证模式

- `walk_forward`
- `rolling_window`
- `expanding_window`
- `purged_kfold`

### 4.3 Purged / Embargo 何时必开

以下场景建议强制启用 `purged + embargo`：

- 标签窗口跨多个未来时间点
- 样本之间有明显重叠持有期
- 高频时序任务
- 事件驱动标签

### 4.4 必须落盘的验证文件

- `validation_scheme.json`
- `training_window_manifest.json`
- `purged_cv_manifest.json`
- `embargo_policy.json`
- `label_overlap_audit.json`

## 5. 横截面特征模板

适用：

- `cross_sectional / equity / daily`
- `cross_sectional / crypto / daily`
- 其他横截面总库

### 5.1 推荐步骤

1. 覆盖率门槛检查
2. 截面缺失值治理
3. 截面去极值
4. `rank normalize` 或 `z-score`
5. 行业 / 市值 / 风险中性化
6. cluster 内去冗余
7. 保存训练窗拟合参数

### 5.2 典型输出

- `cross_section_feature_matrix.parquet`
- `cross_section_transform_params.json`
- `cross_section_coverage_report.json`

## 6. 时序特征模板

适用：

- `time_series / futures / 1min`
- `time_series / options / 1min`
- 其他时序总库

### 6.1 推荐步骤

1. 严格滞后对齐
2. 基于过去窗口计算滚动统计量
3. `rolling z-score`
4. `volatility scaling`
5. `sequence window packing`
6. `regime split`
7. `stationarity diagnostics`

### 6.2 典型输出

- `sequence_feature_tensor.parquet`
- `sequence_window_manifest.json`
- `sequence_alignment_audit.json`

## 7. 降噪、去冗余与降维规范

### 7.1 允许的步骤

- 高相关裁剪
- cluster 代表特征选择
- `mutual information` 预筛
- 树模型重要性预筛
- 受控 `PCA`
- 受控 `AutoEncoder`

### 7.2 不允许的步骤

- 使用未来标签反向决定特征保留
- 未记录版本、参数和解释的黑盒降维
- 在训练窗之外重新估计预处理参数

### 7.3 必须落盘

- `feature_selection_report.json`
- `feature_corr_pruning_report.json`
- `dim_reduction_manifest.json`

## 8. 模型适配层

### 8.1 树模型

适配模型：

- `LightGBM`
- `XGBoost`
- `CatBoost`

输入形态：

- tabular matrix
- 每行一条样本
- 每列一个标准化后的特征

### 8.2 Dense 模型

适配模型：

- `MLP`

输入形态：

- dense feature matrix
- 一般与横截面或低频聚合特征更兼容

### 8.3 序列模型

适配模型：

- `Transformer`
- `TCN`
- `LSTM`

输入形态：

- 序列窗口
- 明确 `sequence_length / stride / horizon`

## 9. Feature Store 规范

### 9.1 最小对象

建议至少具备：

- `Feature Registry`
- `Offline Feature Store`
- `Online Feature Store`
- `Feature Service`
- `Feature Contract`

### 9.2 每个特征应登记的字段

- `feature_name`
- `feature_group`
- `entity_key`
- `event_ts`
- `knowledge_ts`
- `ttl`
- `freshness_sla`
- `owner_team`
- `serving_mode`
- `schema_version`
- `source_factor_ids`

### 9.3 线上线下一致性

必须保证：

- 训练和推理使用同一份特征定义
- 在线特征是离线特征的受控物化或等价实现
- 模型版本能反查对应特征版本

必须产出：

- `online_offline_consistency_report.json`
- `feature_lineage_report.json`
- `feature_freshness_report.json`
- `model_input_schema.json`

## 10. 新鲜度、血缘与退役

### 10.1 新鲜度

每个特征必须设置：

- `freshness_sla`
- `staleness_threshold`
- `late_arrival_policy`

### 10.2 血缘

必须能回答：

- 这个模型用了哪些因子
- 这个因子来自哪个总库
- 是否来自优化工厂
- 是否来自 `Tier 3D`

### 10.3 退役

当特征退役时，必须能追踪：

- 影响哪些模型
- 是否存在在线服务依赖
- 是否有替代特征

## 11. 模型端交付清单

模型组或特征平台组至少需要交付：

- `Feature Registry`
- `Offline Feature Store`
- `Online Feature Store`
- `PIT join builder`
- `validation scheme engine`
- `feature freshness monitor`
- `training-serving consistency checker`
- `feature lineage tracker`
- `model input contract`

## 12. 与因子评估基建组的接口边界

因子评估基建组需要提供给模型组：

- 已评估完成的因子资产对象
- 评分卡和标签
- 可复用图表与审计产物
- `PIT` 安全审计结果
- `feature_store_allowed / online_serving_allowed` 标志

模型组不应反向承担：

- 候选生成
- 候选预检查
- 因子正式登记
- 因子路由与层级入库

## 13. 一句话实施顺序

推荐的实现顺序：

1. 先实现 `Offline Feature Store + PIT join`
2. 再实现训练数据切分与验证引擎
3. 再实现模型适配层
4. 最后补在线特征、统一注册表和一致性审计
