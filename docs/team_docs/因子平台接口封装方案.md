# 因子平台接口封装方案

## 1. 文档目的

本文档面向接口封装组，目标不是解释某个单独算法怎么实现，而是回答下面几个工程问题：

1. 现有仓库已经有哪些能力可以直接复用。
2. 后续要建设的“企业级量化因子评估与自动化入库系统”应该怎样封装成稳定 API。
3. 面对 `LLM / self-evolving / RL / GP / hybrid` 等持续扩展的方法谱系，平台层应该如何抽象，避免每接入一种方法就重做一套接口。
4. 因子层如何与模型层、信号层衔接，确保因子输出后可以稳定进入模型训练和最终信号生产链路。

本文档同时参考了：

- 当前仓库已实现模块：`factor_engine`、`factor_evaluation`、`factor_admission`、`backtest_layer`、`data_access`
- 内部需求文档：`企业级量化因子评估与自动化入库系统需求文档.docx`
- 内部白皮书：`04_量化团队_算法驱动因子挖掘与资产化管理.md`
- **外部治理规范**：`quant_server_governance_api_spec_fixed.pdf` (重点参考 Job/Event/Manifest/权限分层设计)

## 2. 结论先行

### 2.1 核心协作模式：Query + Job + Event
根据治理规范，平台不再是简单的“函数调用”，而是服务化协作：

1. **Query API**：用于轻量级查询（算子、资产元数据、Job 状态、Manifest）。
2. **Job API**：用于耗时任务（计算、评估、物化、回测）。所有重任务必须异步，返回 `run_id`。
3. **Event**：任务完成后发出事件（如 `factor_admitted`），触发下游（如模型层、信号层）动作。
4. **Manifest**：Job 产出的唯一合法交付物，包含结果路径、版本快照和访问控制。

### 2.2 结果权限分层
禁止实习生直接访问原始数据盘。结果必须通过三层投影暴露：
- **Private**：原始因子值、详细日志、调试轨迹（仅限内核开发者）。
- **Internal**：IC/Returns/Metrics/Summary（面向研究组、实习生、模型层）。
- **Public**：脱敏图表、准入结论、看板数据（面向 Dashboard、展示页）。

### 2.3 平台应该围绕 5 条主线封装
建议接口封装组按以下 5 条主线设计：

1. `Discovery Layer (Job API)`
   - 接收不同方法（AlphaPROBE, RL等）产生的候选因子。
   - 统一归一为标准 `CandidateFactor` / `FactorSpec`。

2. `Factor Runtime Layer (Job API)`
   - 对候选因子做校验、编译、执行、物化。
   - 产出包含数据指纹的 `Factor Asset`。

3. `Evaluation & Admission Layer (Job API + Event)`
   - 完成标准化评估、自动路由。
   - 任务完成后发出 `factor_admitted` 或 `factor_rejected` 事件。

4. `Feature Serving Layer (Query API + Job API)`
   - 把通过治理的因子输出为模型可消费的特征视图。
   - 提供特征冻结（Freeze）能力，确保模型训练可复现。

5. `Lifecycle Governance Layer (Query API + Job API)`
   - 监控半衰、拥挤，处理退役与归档。

### 2.3 第一期优先级

第一期不建议优先做复杂的 discovery method 服务化，而应优先做：

1. 因子资产注册
2. 因子校验与运行
3. 因子评估
4. 准入与自动路由
5. 特征视图输出

换句话说，先把“因子工厂主干”做稳定，再把 AlphaPROBE、QuantaAlpha、RL、GP 当作 discovery adapter 接进来。

## 3. 需求文档对平台的核心要求

结合 `企业级量化因子评估与自动化入库系统需求文档.docx`，平台必须满足以下业务约束。

### 3.1 因子不是公式，是资产

需求文档已经明确指出：

- 因子必须具备身份、血缘、版本、状态、标签、评估结果和去向
- 因子需要可追溯、可分层、可路由、可治理
- 聚合器输出、模型输出的 master score 也要重新登记为新资产

因此平台的最小管理对象不能只是一个公式字符串，也不能只是一个 parquet 文件，而必须是标准化 `Factor Asset`。

### 3.2 评估不是一张报表，而是流水线

需求文档提出了从 `Stage 0` 到 `Stage 8` 的分阶段评估逻辑，包括：

- 接入与登记
- 资源与复杂度预检查
- 数据治理
- 预测能力
- 收益风险
- 结构鲁棒性
- 独立性与冗余
- 交易与容量
- 决策与路由
- 超级 Alpha 回流评估

这意味着 API 层不能只提供一个“跑评估”按钮，而应把评估结果封装成结构化 `Metrics Package` 和 `Admission Decision`。

### 3.3 系统必须支持多方法共存

需求文档已经把 `method_code` 设计为主字段之一，并明确：

- 首期聚焦量价总库
- 但架构必须支持多库、多域、多方法、多轮次共存

所以方法层只应作为 metadata 和 adapter，不应成为主业务表结构的核心耦合点。

### 3.4 因子层不是终点，模型层才会产最终信号

这次业务补充非常关键：

- 当前讨论的是因子层
- 因子产出后还要输入模型端
- 模型端再产生最终信号

因此平台必须内建 `Feature Store Ready / Feature View` 这一层，而不是停在 `evaluate + admit`。

## 4. 当前仓库已具备的能力映射

以下内容是面向接口封装组的“现状盘点”，用于区分：

- 哪些已经能复用
- 哪些需要重新包装
- 哪些尚未实现

### 4.1 已具备：因子运行与物化

当前仓库中，`factor_engine` 已具备以下能力：

- 因子 DSL / API 构造
- 编译：Expr -> IR -> Plan
- 执行：backend + datasource
- 单因子运行
- 多因子运行
- 配置驱动运行
- 物化到 factor lake

可视为现成的 `Factor Runtime Core`。

### 4.2 已具备：标准化单因子评估

`factor_evaluation` 已实现：

- 因子值读取
- 市场数据对齐
- IC / RankIC
- 分组收益
- quantile backtest
- long-short returns
- `summary.csv/json`
- `manifest.json`

这已经是需求文档中“预测能力 + 部分收益风险”流水线的早期版本。

### 4.3 已具备：准入与 catalog 记录

`factor_admission` 已具备：

- 读取评估结果
- 规则阈值判断
- manual / rule_based 两类模式
- 写入 admission catalog
- 更新 factor status

这可以直接演进为“默认入库决策 + 自动路由”的第一版。

### 4.4 已具备：回测能力

当前仓库已有两套相关能力：

1. `single_asset_backtest`
   - 单资产目标仓位回测
   - 多资产目标权重回测
   - 标准化 `returns / metrics / summary`

2. `portfolio_backtest`
   - holdings 长表回测
   - 策略注册评估

这些能力后续可接入“收益风险”和“交易摩擦/容量”评估层，但不建议一开始与因子评估完全绑死。

### 4.5 已具备：统一数据访问内核

`data_access` 已提供：

- 统一只读
- 统一写入
- upsert
- publish
- 有限 sql
- registry
- schema / audit / namespace

这是平台底层核心能力，但不应直接暴露给外部实习生或 discovery method 开发者。

### 4.6 已有雏形：Agent 自动化生成

`factor_agent` 已具备：

- 研报 -> YAML
- 评分反馈修订
- 简单多轮 agent loop

但当前更像内部实验工具，不建议第一期就作为正式开放 API。

### 4.7 尚未完整实现：企业级评估超集

对照需求文档，当前仍缺少或不完整的内容包括：

- 复杂度/算力预算预检查
- 未来函数 / 死循环 / 昂贵表达式熔断
- 美股量价专属微观结构指标超集
- 冗余与增量价值评估超集
- 更完整的容量与成本情景分析
- 自动标签引擎
- 自动路由矩阵
- Tier 0~4 立体库拓扑
- Watchlist / deprecated / archived 治理
- Feature Store Ready 正式产出层
- 聚合器输出回流为新因子的递归登记

因此建议接口层设计时必须预留扩展字段，不能只按现有实现最小集合建死。

## 5. 推荐的平台分层

建议把系统拆成 7 层，接口封装时按层管理。

### 5.1 Layer A: Discovery Adapters

作用：

- 接入 LLM、自进化、RL、GP、人工研究等不同来源
- 不直接写入生产库
- 只负责生成候选因子对象

典型来源：

- `llm_agent`
- `self_evolving`
- `graph_evolution`
- `rl`
- `genetic_programming`
- `manual`
- `aggregator`

### 5.2 Layer B: Registry & Identity

作用：

- 创建 `factor_id`
- 写入来源、批次、方法、父因子、血缘
- 管理版本、状态、生命周期

这是需求文档里“户籍登记”的正式系统层。

### 5.3 Layer C: Runtime & Materialization

作用：

- 校验表达式/YAML
- 执行因子
- 生成暴露序列
- 写入 factor lake / staging

这是现有 `factor_engine` 可直接承接的核心层。

### 5.4 Layer D: Evaluation Pipeline

作用：

- 跑标准化评估 Stage
- 形成结构化指标包
- 支持默认模板与扩展模板分离

这层是需求文档的核心。

### 5.5 Layer E: Tagging & Routing

作用：

- 自动打标签
- 评分卡
- route 到不同 Tier
- 决定 reject / incubate / feature store / satellite / core

这一层当前仓库还只有 `factor_admission` 的雏形，需要扩展。

### 5.6 Layer F: Feature Serving

作用：

- 面向模型层导出统一特征视图
- 提供标准样本切片和 schema
- 支持 freeze 和 reproducibility

这是本次新增加的关键层。

### 5.7 Layer G: Lifecycle Governance

作用：

- 复评
- 半衰
- 漂移监控
- watchlist
- deprecated
- archive

这一层一期不必全部实现，但对象模型必须先设计进去。

## 8. API 设计原则

### 8.1 全部重任务异步化

以下任务必须走异步 job：

- discovery
- factor run
- materialize
- evaluate
- admission
- feature view build
- backtest

同步接口只做：

- 校验
- 查询
- 列表
- manifest 读取

### 8.2 统一以 Job + Manifest 返回

不要让接口直接返回大 DataFrame。

统一返回：

- `run_id` (Job ID)
- `status` (queued / running / success / failed)
- `manifest` (任务产物清单)
  - `artifacts` (summary, metrics, returns, logs 等路径)
  - `code_version` (Git SHA)
  - `data_version` (数据水位线/指纹)
  - `config_version` (配置哈希)
  - `visibility` (private / internal / public)

### 8.3 禁止暴露内部路径和内部类

外部响应中不应直接出现服务器真实物理路径（如 `/home/yluel/...`）。所有路径应相对于治理规范定义的 `workspace_data` 或 `results` 根目录，并由 API 屏蔽前缀。

禁止直接暴露：
- `FactorEngine` 内部对象
- `DataAccessStore` 内部路径
- sqlite catalog 物理位置
- staging / publish 目录

### 8.4 输入必须 schema 化

禁止：

- 任意 Python 代码
- 任意 shell 命令
- 任意 SQL
- 任意文件路径

允许：

- 结构化 JSON
- 受控 YAML 模板
- 受控 DSL
- 已注册的数据源别名

## 9. 推荐 API 清单

以下为建议的接口分组。

## 9.1 Catalog API

用于给研究员、实习生、agent、外部方法统一暴露“能用什么”。

### `GET /catalog/operators`

返回：

- 可用算子列表
- 分类
- 参数签名
- 是否 stub
- 依赖字段
- 示例

### `GET /catalog/datasets`

返回：

- 可用数据域
- 数据集别名
- 字段列表
- 频率
- 默认 universe
- 时间范围

### `GET /catalog/templates`

返回：

- `factor_spec`
- `evaluation_template`
- `admission_policy`
- `feature_view_template`

## 9.2 Discovery API

面向方法适配层，不绑定具体算法名字。

### `POST /discovery-jobs`

请求：

- `method_type`
- `domain_code`
- `objective`
- `search_space`
- `constraints`
- `budget`
- `campaign_id`
- `batch_id`

响应：

- `discovery_job_id`
- `status=queued`

### `GET /discovery-jobs/{job_id}`

返回：

- 状态
- 轮次
- 候选数量
- 失败数
- 最优候选摘要

### `GET /discovery-jobs/{job_id}/candidates`

返回候选因子列表。

说明：

- AlphaPROBE、QuantaAlpha、RL、GP 后续都接入这一层
- 不单独暴露方法专属主接口

## 9.3 Candidate / Spec API

### `POST /candidate-factors`

用于手工或外部方法直接提交候选。

请求：

- `source_type`
- `raw_formula`
- `raw_yaml`
- `raw_code`
- `hypothesis_text`
- `metadata`

### `POST /factor-specs/normalize`

作用：

- 将候选归一为平台可执行 `FactorSpec`

### `POST /factor-specs/validate`

作用：

- 校验 DSL / YAML / 数据依赖 / 复杂度

返回：

- `valid`
- `errors`
- `warnings`
- `required_columns`
- `lookback_hint`
- `operator_usage`
- `contains_stub_ops`
- `complexity_score`

## 9.4 Factor Asset API

### `POST /factor-assets/register`

作用：

- 创建正式资产对象
- 分配 `factor_id`
- 记录来源、父因子、版本、主键身份

### `GET /factor-assets/{factor_id}`

返回：

- 元信息
- 当前状态
- 当前 tier
- 最新 run/eval/decision

### `GET /factor-assets/{factor_id}/lineage`

返回：

- 父因子
- 衍生关系
- campaign / batch 来源

## 9.5 Runtime API

### `POST /factor-runs`

作用：

- 对 `FactorSpec` 发起一次运行

请求：

- `factor_id` 或 `factor_spec_id`
- `data_scope`
- `runtime_profile`
- `save_result`

响应：

- `factor_run_id`

### `GET /factor-runs/{run_id}`

返回：

- 状态
- 执行摘要
- 行数
- 非空率
- 耗时
- 日志

### `POST /factor-runs/{run_id}/materialize`

作用：

- 将结果写入 factor lake / staging

返回：

- `rows_written`
- `partitions`
- `watermark`
- `materialization_id`

## 10. 自动路由建议

当前仓库只有基础准入逻辑，建议按需求文档扩展到多路径路由。

### 10.1 默认决策枚举

建议支持：

- `hard_reject`
- `soft_reject`
- `incubate`
- `accept_satellite`
- `accept_core`
- `accept_feature_store`
- `watchlist`

### 10.2 默认路由规则建议

#### 直接归档

条件：

- 语法非法
- 命中未来函数
- 计算超时
- 表达式复杂度超限
- 多项核心指标失效

去向：

- `archived`

#### 送医院 / 孵化

条件：

- 预测力强
- 但换手高、拥挤高、相关性过高、容量差

去向：

- `incubating`

#### 进入核心 / 卫星

条件：

- 通过硬门槛
- 风险收益、结构稳定性、容量、正交增量均达标

去向：

- `production_core` 或 `production_satellite`

#### 进入特征池

条件：

- 单因子不一定适合直接交易
- 但适合作为模型输入特征

去向：

- `feature_store_ready`

这条路在你们体系里非常重要，因为它直接承接“因子 -> 模型”的链路。

## 11. 不建议开放给接口使用方的内容

接口封装组要特别注意权限边界。

### 11.1 不应暴露源码层内核

不要直接对外暴露：

- `Analyzer`
- `Lowerer`
- `Optimizer`
- `Backend`
- `ExecutionContext`
- `CacheManager`
- `DataAccessStore`

### 11.2 不应暴露底层数据写入能力

不要让调用方直接用：

- `write_arrow`
- `upsert`
- `publish_from_staging`
- `sql`

这些能力只能由平台内部服务调用。

### 11.3 不应暴露真实物理路径

不要在 API 返回里写：

- factor lake 真实路径
- published / staging 根路径
- catalog sqlite 路径
- 本地数据盘地址

### 11.4 不应开放任意脚本执行

不要提供：

- 任意 Python 代码提交执行
- 任意 shell
- 任意 SQL

如果后续一定要支持代码型方法，必须走受限 sandbox + artifact 化输出。

## 15. 最终建议

### 15.1 一句话版本

不要把平台设计成“某个因子挖掘算法的 API 网关”，而要把它设计成“因子资产工厂 + 评估路由系统 + 模型特征输出平台”。

### 15.2 对当前项目的最合适落法

对于当前仓库，最建议的建设顺序是：

1. 以 `factor_engine` 为 runtime core
2. 以 `factor_evaluation` 为 evaluation v1
3. 以 `factor_admission` 为 routing/admission v1
4. 新增 `factor registry` 和 `feature view` 两层
5. 让 AlphaPROBE / QuantaAlpha / RL / GP 后续都作为 `discovery adapter` 接入

### 15.3 对实习生与外部方法开发者的开放边界

他们应当能做的是：

- 提交候选因子
- 校验表达式
- 发起评估
- 读取结构化产物
- 导出模型特征视图

他们不应当能做的是：

- 直接访问核心引擎源码
- 直接写 factor lake
- 直接调用底层 publish/upsert/sql
- 获取真实内部数据路径与生产库结构
