1 文档目标与治理原则
1.1 文档目标
本规范的目标是建立一套可执行的服务器治理与模块协作标准，使量化投研平台在多人协作、双服务器部
署和多模块联调场景下保持稳定、可审计、可回滚和可扩展。
核心治理目标
代码可追踪，数据可回滚，任务可审计，结果可分层，权限可回收。
本规范重点解决以下问题：
‧ Server A / Server B 的职责边界如何划分；
‧ 不同模块如何在不暴露内部目录和密钥的前提下协作；
‧ 同步查询、异步任务、事件通知三类接口如何分工；
‧ 任务执行结果如何通过 Manifest 暴露给下游；
‧ 后续维护人员如何安全地查看、运行、排查和交接系统。

4 统一 Environment 与配置管理
4.1 统一 Environment 策略
当前阶段优先采用统一平台环境，减少多人协作、迁移和联调成本。长期在服务边界稳定后，可逐步拆分
为 data、factor、strategy、backtest、job_api 等服务级环境。
阶段
短期迁移阶段
中期稳定阶段
长期生产阶段

Environment 策略
使用统一 Python Runtime 和统一平台环境，例如
/srv/quant/envs/platform/，确保所有模块能按同一依赖口径跑通。
保持统一 Python 主版本和统一配置规范；对资源边界清晰的模块逐步拆分服
务级环境。
形成平台统一基础镜像 + 模块独立依赖锁定，避免单个模块升级影响全平台。

4.2 推荐规范
‧ Python 主版本统一，例如 Python 3.11。
‧ 根目录保留统一依赖入口；开发测试依赖与运行依赖应清晰区分。
‧ 每个模块必须提供 .env.example，声明需要的环境变量。
‧ 真实生产配置统一放在 /srv/quant/configs/<module>/prod.env。
‧ systemd 服务统一通过 EnvironmentFile= 加载生产环境变量。
‧ 禁止将真实 prod.env、API Key、云密钥、数据库密码写入 Git。

6 模块 API 文档规范
6.1 为什么必须先写接口文档
多人协作时，模块之间不能依赖口头约定或直接读取对方内部脚本。每个模块应先提供稳定的接口文档，
再进行联调。接口文档是模块边界、权限边界、数据契约和任务契约的共同依据。
接口治理原则
模块可以内部快速迭代，但对外暴露的输入、输出、Job、Event 和 Manifest 必须稳定、可测试、可
追踪。

7.2 Query API
Query API 只负责查询，不负责触发重计算。典型接口如下：
GET /api/jobs/{run_id}
GET /api/artifacts/{run_id}/manifest
GET /api/factors/{factor_id}/summary
GET /api/backtests/{run_id}/summary
GET /api/strategies/{strategy_id}/card
GET /api/data-quality/{dataset_id}/summary

Query API 的返回结果应当是授权后的投影结果，不应直接返回 private 目录路径、服务器绝对路径、
完整原始日志或密钥字段。

Job API 负责接收请求、校验权限、写入审计、进入队列、分配 worker，并返回 run_id。调用方不直接
执行脚本，也不登录目标服务器。

8.6 服务化协作方式
模块之间不直接跨服务器 SSH 执行脚本，也不直接读取对方 private 目录。推荐协作方式如下：

和审计日志控制。

9 迁移、上线与回滚流程
9.1 迁移目标
迁移的目标不是简单复制文件，而是将原内网服务器上的单用户代码资产，转换为腾讯云 Server A /
Server B 上的可治理工程平台。

9.2 迁移流程
1. 原服务器盘点：盘点 Git 状态、未提交代码、数据目录、环境依赖、定时任务、后台服务、日志、密
钥和端口。
2. 代码 Git 化：所有代码必须进入 Git；未提交改动建立 migration snapshot commit 和 tag。
3. 新服务器初始化：创建用户组、服务账号、/srv/quant 目录、数据盘挂载和基础依赖。
4. Environment 统一：创建平台统一环境，安装根依赖和模块需要的 editable package。
5. 配置迁移：将真实配置迁入 /srv/quant/configs/<module>/prod.env，不进入 Git。
6. 数据迁移：raw、cleaned、workspace_data 分层迁移；优先使用 rsync dry‑run 验证。
7. 服务部署：使用 systemd 托管 Job API、数据任务、因子任务、回测任务和 Dashboard API。
8. 双跑验证：新旧服务器并行 1‑3 天，对比行数、日期覆盖、symbol 覆盖、Job 输出和日志异常。
9. 正式切换：冻结旧服务器写入，最后一次同步，切换 API / Job 入口。
10. 回滚窗口：旧服务器至少保留两周，关键节点创建腾讯云快照。

10.1 systemd 服务托管
生产常驻服务不得长期使用 nohup python xxx.py & 管理。统一使用 systemd，便于开机自启、日志
查询、失败重启和权限控制。
[Unit]
Description=Quant Job API Service
After=network.target
[Service]
User=svc-jobapi
Group=quant-ops
WorkingDirectory=/srv/quant/repos/quantsociety_backend
EnvironmentFile=/srv/quant/configs/job_api/prod.env
ExecStart=/srv/quant/envs/platform/bin/python -m job_api.main
Restart=always
RestartSec=5
[Install]
WantedBy=multi-user.target

常用命令：
sudo systemctl status quant-job-api
sudo systemctl restart quant-job-api
journalctl -u quant-job-api -f
