## 1. 总则

### 1.1 目标 [强制]

- **正确性**：回测、数据管线可复现、防未来函数与错误对齐。  
- **可维护性**：他人可在合理时间内接手（见命名与模块边界）。  
- **可审计性**：重要读写与发布有迹可循（`data_access` 审计、git）。  
- **安全**：不误删生产目录、不泄露密钥、共享账号下注意路径隔离（namespace）。

### 1.2 适用范围

本仓库内 Python 与配置；各子项目若有额外规范须显式成文。

## 2. 数据访问 [强制] / [建议]

### 2.1 [强制] 经 data_access 读数

- 业务层禁止 `pd.read_parquet` / `pq.read_table` / `import duckdb`（**例外**见 `.data_access_allowlist.yaml`）。  
- 新数据先登记 `data_access/config/datasets.yaml`，再 `get_store()` 调用。  
- **published 禁止直写**；更新走 staging → `publish_from_staging`（见文档一 §9）。  

**为何**：直读绕过**白名单与审计**，同一数据在三人机器上可能路径不一致，生产事故难追溯。  
**反例**：`pd.read_parquet("/mnt/team/xxx/2020.parquet")` 合入主干（应登记为 dataset 后 `read_frame(...)`）。  
**正例**：见文档一 §10 示例；只改 `YOUR_DATASET_NAME` 与列名。

### 2.2 [建议] 性能习惯

- 大表优先 `read_arrow` / `read_arrow_stream`；复杂变换可考虑 `scan_polars`。  
- 多列需求优先 `load_columns` 一次取齐，避免循环单列反复扫盘。  
- 优先向量化，避免在热路径上大规模 Python `for` 逐行扫描（**见 §6**）。

**为何**：循环 `read_frame` 十次 ≈ 扫盘十次；`load_columns` 一次扫描多列更省 IO。API 细节见文档一，此处不重复。

<a id="s23-allowlist"></a>

### 2.3 allowlist 与 `data_access` 静态检查

> **与文档一的分工**：[01](01_data_access_duckdb_全量变更与迁移指南.md) 写 **`.data_access_allowlist.yaml` 分节与含义** 及技术接口；**本节写合入时谁审、怎么跑检查**。

#### 2.3.1 [强制] 为何要有 allowlist

- 全仓默认**禁止**业务代码中 `import duckdb`、`pd.read_parquet` / `pq.read_table` 等直读（与 **§2.1** 一致）；**确需直读**的（如 `data_access` 自实现、流式按文件 merge、raw 逐文件清洗）**必须**在 [`.data_access_allowlist.yaml`](../../.data_access_allowlist.yaml) 中**用路径 + reason 显式登记**。  
- **合入前**：增删 allowlist 条目的 PR **须**有评审人理解「**为何**不能改写成 `get_store`」；**禁止**为省事批量放宽。

#### 2.3.2 [建议] 如何运行检查脚本

- **全仓扫描**（以仓库根为 CWD）：

  ```text
  python scripts/check_data_access_allowlist.py
  ```

- **单文件**（适合 pre-commit 或只改一个模块时快扫）：

  ```text
  python scripts/check_data_access_allowlist.py path/to/your_file.py
  ```

- 退出码：`0` 无违规；`1` 有未豁免的直读/duckdb 连接等；`2` 脚本自身或 yaml 问题（详见脚本 docstring，与 [01 §13](01_data_access_duckdb_全量变更与迁移指南.md#s13-allowlist) 一致）。

#### 2.3.3 [管理目标] 与 CI

- 若团队 pre-commit 已接该脚本，**本地不通过**则勿推；**未接**时至少在 PR 描述中写「**已** `python scripts/check_data_access_allowlist.py` 通过」或说明豁免理由。

#### 2.3.4 [建议] 新增豁免的写法

- 在 yaml **合适分节**（A 实现体 / B 流式写 / C raw / D factor_engine / …，以文件内说明为准）增加：

  ```yaml
  - path: your/pkg/module.py
    reason: "一句话：为何必须直读/直连 duckdb，以及计划何时收敛"
  ```

- 路径可 **glob**（见脚本注释与 yaml 头说明）。

## 3. 工程与目录 [强制] / [建议]

### 3.1 [强制]

- 正式交付**不得**以 **Jupyter notebook（.ipynb）** 作为**唯一**交付物；须沉淀为可 import 的模块 + 测试。探索性 ipynb 可保留在个人目录，不替代主干代码。  
- 配置与超参**不得**长期硬编码在脚本唯一副本；须可外部化（yaml/json/环境变量，按子项目已有约定）。  
- 新增能力须有**可运行**的**最小测试**或可复现入口（新模块至少 smoke）。

**为何**：ipynb 难 diff、难在 CI 里复现，接手人无法稳定 import 你的逻辑。  
**反例**：只提交 `research.ipynb` 无 `.py`、无 `pytest`。  
**正例**：`strategies/mom3d/loader.py` + `tests/test_mom3d.py`，notebook 只作探索附录。

### 3.2 [建议]

- 单函数不宜过长；职责单一。  
- 避免复制粘贴逻辑；共用的抽到 `data_access`、工具库或子包。

---

## 4. 编码与注释 [建议]

- 公共 API 与**非显然**的数学/金融假设须有简短 docstring 或注释。  
- 命名体现**时区、单位、复权、对齐**等语义，避免 `df1` / `tmp`。  
- 关键约束（如「此处禁止向前看」）在代码旁**点明**。

**示例（命名）**：`prices_tze_asia_1d` 优于 `p`；`label_shifted_1d` 优于 `y`。

---

## 5. 测试 [强制] / [建议]

### 5.1 [强制]

- 对 `data_access` 与公共数据路径的修改须配合 **contract / unit** 测试（视改动范围）。  
- 与**文件系统、删目录、发布**相关逻辑**必须**有测试覆盖**安全边界**；测试中使用 **`tmp_path`** 或专用临时根，**禁止**对仓库工作区根无界 `rmtree`（见文档一 [§15](01_data_access_duckdb_全量变更与迁移指南.md#s15-cwd) 与 [§14 测试与安全网](01_data_access_duckdb_全量变更与迁移指南.md#14-测试与安全网)）。

**为何**：删目录逻辑一旦误触 CWD 会毁仓；必须在 `tmp_path` 下**证明**只删了该目录。  
**反例**：`shutil.rmtree(".")` 或 `rmtree(Path.cwd() / "output")` 而 `output` 未在测试中固定。  
**正例**：`def test_foo(tmp_path): d = tmp_path / "out"; d.mkdir(); ... rmtree(d)`，断言不碰仓库根。

### 5.2 [建议]

- 回测/策略关键路径逐步增加**回归**或 golden 测试。  
- CI 在 `.github` 或团队流程中应跑与改动相关的子集 `pytest`。

## 6. 性能 [建议]

- 能 **NumPy / pandas / Polars 向量化** 的，不手写大循环。  
- 大结果落盘时考虑**分块、流式、分区**。  
- 并行/多进程须考虑**读共享、显存/内存**上限与**数据竞争**。

**为何与模型文的关系**：更重的**结构、超参、过拟、验证切分、消融**取舍见 [03 篇七](03_量化团队_模型与实验规范.md#generalization-tuning) 与 [篇八 验证与 WFO](03_量化团队_模型与实验规范.md#validation-experiments)。本节只强调实现层**别用 Python 大循环**替代向量化。

## 7. 输出、日志与文件命名 [建议]

### 7.1 统一推荐格式（可按组内微调）

- **目录/实验**：`<作者简写>_<YYYYMMDD>_<任务或模型名>_<v版本>`，例：`hwx_20260421_mom3d_v2`。  
- **模型权重/指标**：在文件名中体现**作者、时间、数据区间、版本**；可附加 **git 短 hash**。  
- **日志**：可检索，避免无意义刷屏；生产路径禁止用 `print` 替代结构化日志（若子项目有 logging 标准须遵守）。

**为何**：半年后只看文件名能知道**谁、何时、用哪段数据、第几版**，避免 `final_v2_real.py` 式混乱。

### 7.2 [强制] 相关

- 输出路径**不得**指向其他成员的 namespace 或 published 区（除非经授权与代码审查）。  
- 不将密钥、口令写入仓库与日志。

## 8. 回测与因子开发 [强制] / [建议]

### 8.1 [强制]（原则）

- **禁止未来函数**：特征、标签、归一化所用信息不得使用未来数据（含全局均值未滚动计算等）。  
- 时间、标的、频率**对齐**口径在策略文档或代码中明确。  
- 读数据**只走 data_access**（见 §2）。

### 8.2 [建议]（与模型实验的划分）

- 回测**验证方式**、walk-forward、基线对照、收益声称如何做得**站得住脚**，见 [03 从篇三至篇八](03_量化团队_模型与实验规范.md#P03-part3)（[篇三 问题类型](03_量化团队_模型与实验规范.md#paradigm-cross-time) 起，经 [篇五～六](03_量化团队_模型与实验规范.md#P03-part5)、[篇八 WFO](03_量化团队_模型与实验规范.md#wfo-gap)）；本文 **§8.1** 的底线**仍须同时满足**。

## 9. 删路径、清理与「危险 API」[强制]

- `shutil.rmtree`、`Path.glob`+删除、清空目录等**必须**审查**目标路径**是否**显式、白名单、可测试**。  
- **禁止**用 `Path()` 无参作为「空标记」与删除逻辑结合（事故说明见文档一 [§15](01_data_access_duckdb_全量变更与迁移指南.md#s15-cwd)）。  
- 发布/迁移脚本**不得**在「成功分支」对当前工作目录做未约束删除。
