# 因子评估全链路逻辑链与对象流

本文档用于给因子挖掘组、因子评估组、平台工程组和下游基建组提供同一套全链路视图。目标只有一个：把候选因子从产生到最终评估、入库、复评、退役的完整 pipeline 讲清楚，避免不同团队各自理解一套流程。

## 1. 适用范围

- 首期范围：美股日频横截面量价因子。
- 上游来源：LLM、RL、GP、论文公开方法、GitHub 开源实现、人工构造。
- 下游对象：因子评估、标签治理、准入路由、因子库管理、特征供给、组合研究。
- 文档重点：讲清楚对象、状态、文件、表、接口、责任边界，不展开已有算子层细节。

## 2. 一句话总览

整个系统是一条 24h 持续运行的多方法因子生产线：上游多种挖掘方法并行提交候选因子，系统按大轮和 iteration 组织批次，先完成预检查和去重，再复用现有因子执行能力产出标准暴露文件，随后统一评估、贴标签、准入路由，并将通过的因子送入核心库、卫星库或特征原料库；未通过的因子进入医院、观察区或归档库，后续继续复评、修复或退役。

## 3. 角色与对象

### 3.1 角色分工

- 因子挖掘组：持续运行 LLM、RL、GP、公开方法和人工研究，向系统提交候选因子。
- 因子评估组：定义评估模板、准入策略、标签规则和复评机制。
- 平台/基建组：建设对象模型、存储、任务编排、路由、审计、查询和可观测性。
- 下游策略/组合团队：消费通过准入的因子、特征和回测产物。

### 3.2 核心对象

- `campaign`：一轮大规模挖掘活动，例如一次 GP 大轮、一轮 LLM Prompt Sweep、一轮论文复现批次。
- `iteration`：同一 `campaign` 下的单轮迭代，例如第 3 轮变异、第 5 次自反修正、第 2 次超参重采样。
- `candidate_factor`：尚未进入正式因子湖的候选对象，包含表达式、来源、复杂度和父因子关系。
- `factor_asset`：完成登记后的正式因子资产对象，具备唯一 ID、血缘、版本、状态、标签和评估记录。
- `evaluation_run`：一次标准评估执行记录。
- `admission_decision`：一次准入决策记录。
- `route_record`：一次路由动作记录，例如送医院、入核心库、进观察区。

## 4. 顶层逻辑链

### 4.1 总链路

```text
多方法挖掘器持续运行
-> 以 method / campaign / iteration 组织候选批次
-> 提交 Candidate Submission
-> 预检查与去重
-> 候选通过后登记 factor_id
-> 复用现有 factor_engine 执行并物化因子暴露
-> 先写入 factor_lake_staging
-> 校验通过后发布到 factor_lake
-> 运行标准 factor_evaluation
-> 生成 MetricsPackage 与评估产物
-> 运行准入与贴标签
-> 生成 AdmissionDecision / TagPackage / RouteRecord
-> 路由到核心库 / 卫星库 / 特征原料库 / 医院 / 观察区 / 归档区
-> 下游组合、策略、特征聚合层消费
-> 持续复评、监控、降级、修复或退役
```

### 4.2 按对象展开的主链

```text
Method Runtime
-> campaign_id
-> iteration_id
-> batch_id
-> candidate_factor.json
-> precheck_report.json
-> factor_id / factor_registry
-> factor_exposure parquet
-> evaluation artifacts
-> admission decision
-> route target tier
-> production / incubator / archive
```

## 5. 全链路详细说明

### Stage 0. 多方法候选产生

上游不是单一来源，而是长期并发运行的多方法挖掘器。首期建议统一收敛到以下来源枚举：

- `llm`
- `rl`
- `gp`
- `paper`
- `oss_repo`
- `manual`
- `aggregator`

每个来源都必须带上统一批次信息：

- `method_code`
- `campaign_id`
- `iteration_id`
- `batch_id`
- `parent_factor_ids`
- `creation_ts`
- `complexity_profile`

这样做的目的不是为了形式统一，而是为了在后面评估失败、重复发现、变异追踪和多重检验治理时，能够准确回溯“这个因子是在哪一轮、哪种方法、从哪些父因子演化出来的”。

### Stage 1. 候选提交

上游提交进入系统的不是自由文本，而是结构化候选对象。建议最小提交体包括：

- `factor_expression`
- `formula_ast` 或等价结构
- `method_code`
- `campaign_id`
- `iteration_id`
- `batch_id`
- `parent_factor_ids`
- `complexity_profile`
- `rationale_summary`
- `resource_hint`

说明：

- `campaign_id` 用于标识大轮。
- `iteration_id` 用于标识同一大轮下的内部迭代。
- `batch_id` 用于标识具体一次运行提交。
- `complexity_profile` 是预检查的重要输入，不允许缺失。

### Stage 2. 预检查与去重

这一步的目标是把明显非法、重复、过重的候选在进入正式评估前挡住，避免拖垮整条流水线。

预检查至少包括：

- 语法合法性检查
- 未来函数检查
- AST 深度和算子数量检查
- 单截面预计耗时与内存预算检查
- 重复发现：`ast_hash`、`semantic_hash`、数值指纹
- 运行熔断：死循环、超时、超内存

输出产物建议：

- `precheck_report.json`
- `dedup_result.json`
- `candidate_status = passed / rejected / duplicate / timeout`

### Stage 3. 因子登记与户籍创建

通过预检查的候选，才会被正式登记成因子资产对象。

登记动作包括：

- 分配 `factor_id`
- 写入 `factor_registry`
- 建立 `factor_lineage`
- 记录 `current_state = screening_passed`
- 记录 `current_tier = tier0_raw` 或 `tier1_eval_pending`

从这一步开始，系统里的主角就不再是“候选表达式”，而是“因子资产对象”。

### Stage 4. 因子执行与物化

这一层复用现有 `factor_engine`，下游无需重复建设表达式算子层。

当前仓库已具备：

- 因子 DSL 与算子执行能力
- 基于配置的执行入口
- 因子物化到 factor lake 的能力
- factor catalog 与水位线管理

建议统一执行输出为：

- `datetime`
- `asset`
- `value`
- `year=YYYY` 分区 parquet

首期物理写入路径建议沿用当前实现：

- `factor_lake_staging`
- `factor_lake`

主流程：

```text
candidate_factor
-> factor_engine.run / materialize
-> factor_lake_staging/factors/{factor_id}/year=YYYY/*.parquet
-> schema / row count / watermark 校验
-> publish_from_staging
-> factor_lake/factors/{factor_id}/year=YYYY/data.parquet
```

### Stage 5. 标准评估

这一层复用现有 `factor_evaluation`。首期应以现有可运行评估链为基线，再逐步增强，而不是另起一套评估器。

当前已具备的评估主项：

- IC / RankIC
- horizon 维度评估
- 分位分组回测
- long-short 收益表现
- summary / parquet 标准产物

首期建议标准输出：

- `summary.csv`
- `summary.json`
- `daily_ic.parquet`
- `daily_rank_ic.parquet`
- `quantile_period_returns.parquet`
- `quantile_backtest.parquet`
- `long_short_returns.parquet`
- `manifest.json`

### Stage 6. 贴标签与准入

评估之后不是简单的“通过/不通过”，而是进入标签与路由层。

建议标签分为五类：

- 来源标签：`method_code`、`campaign_id`、`iteration_id`
- 性能标签：高 IC、低 IC、高 Sharpe、高换手等
- 风格标签：量价反转、动量、波动率敏感、拥挤风险等
- 生命周期标签：new / incubating / production / watchlist / archived
- 动作标签：accept_core / accept_satellite / accept_feature_store / incubate / reject

准入层输出建议：

- `AdmissionDecision`
- `TagPackage`
- `RouteRecord`

### Stage 7. 路由到不同库层级

通过评估和准入后，因子不会只进入一个统一大仓库，而是进入不同功能区。

建议首期采用以下逻辑分层：

- `tier0_raw`：原始候选落地区
- `tier1_eval`：评估执行区
- `tier2_incubator`：高潜但存在硬伤，需要平滑、正交、降频或修复
- `tier3a_core`：核心生产因子库
- `tier3b_satellite`：卫星生产因子库
- `tier3c_feature`：特征原料库，供聚合器或更高层模型消费
- `tier4_archive`：归档与负样本库

典型路由规则：

- 预测力弱且多项指标失效 -> `tier4_archive`
- 预测力强但换手高 / 相关性高 -> `tier2_incubator`
- 单因子可直接服务组合 -> `tier3a_core` 或 `tier3b_satellite`
- 单因子一般但对聚合模型有价值 -> `tier3c_feature`

### Stage 8. 下游消费

下游消费有三条典型路径：

- 单因子继续研究与人工复核
- 进入组合构建和策略回测
- 进入特征池供非线性聚合器使用

现有仓库已具备：

- 单资产回测标准协议
- 组合回测标准产物
- data_access 统一读写入口

因此下游应优先复用已有产物和目录协议，而不是各自再造一套落盘格式。

### Stage 9. 持续复评与退役

入库不是终点。进入核心库、卫星库或特征原料库的因子，都必须接受持续复评。

持续治理建议包括：

- 定期重跑标准评估
- 监控 IC 衰减和收益衰减
- 监控相关性飙升和拥挤风险
- 触发 watchlist / downgrade / deprecate / archive

## 6. 物理对象与技术栈

### 6.1 首期建议沿用的现有栈

- 因子执行：Python + `factor_engine`
- 数据访问：`data_access` + DuckDB 统一读写
- 因子湖：Parquet + Hive 风格分区
- Catalog：SQLite
- 评估产物：CSV / JSON / Parquet
- 回测产物：CSV / JSON
- 配置协议：YAML

### 6.2 建议作为扩展目标的技术栈

- 控制面：PostgreSQL
- 指标宽表 / 历史面：ClickHouse
- 产物对象存储：MinIO
- 调度编排：Airflow / Prefect
- 队列：Kafka / RabbitMQ
- 缓存：Redis

说明：首期不要求一次性全部服务化，但文档和对象命名应为后续服务化预留稳定接口。

## 8. 三个完整示例

### 示例 1. GP 因子从大轮到入医院

```text
method_code = gp
campaign_id = gp_us_pv_2026q2_round01
iteration_id = iter_07
batch_id = 20260502_night_03

GP 产生 3,000 个候选
-> 预检查后保留 420 个
-> 语义去重后剩 180 个
-> 登记 factor_id
-> 物化到 factor_lake_staging
-> 发布到 factor_lake
-> 标准评估
-> 发现其中某因子 rank_ic 很强，但 turnover 过高、capacity 偏弱
-> 打标签：high_ic / high_turnover / incubate_candidate
-> 路由到 tier2_incubator
-> 后续平滑、降频后再评估
```

### 示例 2. LLM 因子从 iteration 修正到进入特征原料库

```text
method_code = llm
campaign_id = llm_us_pv_promptset_a
iteration_id = iter_05

LLM 基于公开方法和模板生成候选表达式
-> 第 1 次评估未通过，原因是单调性弱
-> 继续第 5 轮 iteration 修正表达式
-> 新候选通过预检查并物化
-> 评估结果显示单因子收益一般，但与现有核心库相关性低
-> 打标签：low_corr / feature_useful
-> 路由到 tier3c_feature
-> 供下游聚合模型使用
```

### 示例 3. 论文公开方法复现后直接进入核心库

```text
method_code = paper
campaign_id = paper_replication_alpha101_wave02
iteration_id = iter_01

研究员按论文和公开仓库复现量价因子
-> 候选提交
-> 预检查通过
-> factor_engine 物化到 factor_lake
-> factor_evaluation 评估通过
-> admission 判断通过且单因子可直接服务组合
-> 路由到 tier3a_core
-> 下游组合信号与持仓生成直接消费
```

## 9. 下游基建组最需要明确的事情

- 上游候选不是一次性提交，而是 24h 连续提交，必须按 `method / campaign / iteration / batch` 管理。
- 首期不需要重做表达式算子层，应复用现有 `factor_engine`。
- 首期因子暴露文件、评估产物、回测产物都应优先对齐现有目录与 schema。
- 首期建设重点不是“重新发明评估公式”，而是“把对象模型、状态机、路由、存储和审计串起来”。
- 所有新的控制面和 API 设计，都要能映射回当前已经存在的文件产物与运行结果。
