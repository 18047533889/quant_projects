# `data_access` 架构设计与取舍

> 给要改这个模块、或者在 review PR2+ 代码的同学看的。

## 0. 背景：我们要解决什么问题

量化团队的原始状态：

- `factor_layer / backtest_layer / strategy_layer / demo / streaming` 都在自己 `pd.read_parquet`
- 加新数据集要改 5~10 个文件
- 并发跑的时候每个进程各自一份 DuckDB / pandas footer cache
- 路径硬编码，换目录布局所有代码都要改
- 共享 Linux 账号 (`yluel`)，个人实验数据没隔离，容易互相覆盖

PR1 的目标：**把读路径收敛到一处，性能一次做到位，并发/多人场景不留坑**。
不在 PR1 做：写 / 发布 / SQL escape hatch / Polars 适配（PR2+）。

PR2 的目标：**把写路径也收敛，引入审计，但先只开 namespaced/staging**。
`published` 直写永远禁止；`publish_from_staging` 先占位 API，等 PR3 配合发布流程一起做（原子切换、旧版本归档、审批门）。

## 1. 关键设计决策

### 1.1 DuckDB in-memory 单例 + per-call cursor

**方案**：进程启动时 `duckdb.connect(":memory:")` 一次，每个查询 `conn.cursor()` 再执行。

**为什么不是每线程一个 connection**：`:memory:` 连接之间**不共享** buffer pool / object cache。
我们负载的特征是「少量数据集，多线程并发读相同 parquet」——
跨线程共享 footer cache 的收益远 > cursor 带来的那点上下文开销。

**为什么不是进程池**：进程间也不共享 cache，而且 Python 的 fork 会把 DuckDB 内部状态带到子进程，
非常容易出奇怪的 bug。用线程池 + DuckDB 内部并行（`PRAGMA threads=...`）更稳。

**反例**：`data_access/tests/concurrency/test_thread_safety.py` 就是用来锁定这个选择的。
16 线程并发读同一数据集行数必须稳定，别随便去掉。

### 1.2 `enable_object_cache=true`

DuckDB 的 parquet footer（schema / row group stats / 分区元信息）跨查询复用。
对我们这种「同一批文件反复读不同列」的负载，一般第二次查询直接省掉 footer 解码，快 2~5x。

副作用：占一点内存（通常 <100MB），但换来的吞吐值得。

### 1.3 Arrow 零拷贝作为主路径

`read_arrow()` 返回 `pa.Table`，底层走 DuckDB 的 Arrow streaming path。
`read_frame()` 在 Arrow Table 上调 `to_pandas(self_destruct=True, split_blocks=True)`。

**为什么不直接 `.df()`**：DuckDB 的 `.df()` 走 pandas object path，大表（>100M 行）会明显慢，
而且内存峰值高。Arrow → pandas 的路径可以用 `self_destruct` 转完立刻释放底层 buffer，内存打一半。

**`load_columns` 专用路径**：一次 SQL 拿齐所有要用的列，再在内存里按列拆分成 Series。
这是老代码的 3~10x 提速来源——老代码每列都要重新扫 parquet footer、重读时间/标的列。

### 1.4 结构化谓词 ≠ SQL escape hatch

`time_range` 和 `instrument_filter` 是白名单字段，由 `predicate.compile_predicate` 编译成参数化 SQL（`?` 绑定）。

**为什么不开 `store.sql(query)`**：一旦开，路径白名单、审计日志都绕得过去，
未来想做「发布前校验」「预算配额」等一切治理特性都要重写。PR2 会限制性地开放（只读 + 必须带 dataset 名）。

### 1.5 数据集登记驱动

`config/datasets.yaml` 是单一事实来源。`registry.py` 启动时把它加载成：

- `StaticDataset`：路径固定，可以预注册成 DuckDB VIEW
- `ParametricDataset`：有 `{param}` 占位符（例：`factors/{factor_id}`），调用时带 `factor_id=...`

**为什么不把所有数据集都注册成 VIEW**：参数化数据集的 factor_id 空间无限，
预注册要么遍历所有可能值（不现实），要么延迟注册（和直接 `read_parquet(?)` 等价，没省）。
所以静态走 VIEW，参数化走 `read_parquet(?)` + 运行时绑定。

### 1.6 `${VAR:-default}` 展开

自己写了个 `expand_env()`（`paths.py`）而不是用 `os.path.expandvars`。
`expandvars` 不支持 bash 风格的默认值语法（`${VAR:-default}`），
但 YAML 里我们经常要写「开发机用 A、生产用 B」这种兜底路径。

## 2. 三层 access_mode 的设计

| mode | 能读 | 能写（PR2 已实装） | 路径模板 |
|---|---|---|---|
| `published` | 全员 | **禁止直写**（`ValidationError`），只能走 PR3 `publish_from_staging` | 无 `${RUN_NAMESPACE}` |
| `namespaced` | 全员（各自的） | 各自 namespace，`write_arrow` 直写 | 含 `${RUN_NAMESPACE}` |
| `staging` | 发布候选人 | 发布候选人，`write_arrow` 直写 | 含 `${RUN_NAMESPACE}` 前缀 |

**为什么不用 OS 文件权限**：共享账号 `yluel` 下所有人 `uid` 一样，OS 权限没区分能力。
只能靠路径层面的 namespace 隔离 + 代码层面的 `PathAuthorizer` 白名单。

**`PathAuthorizer.resolve_and_authorize`** 的意义：把 glob 的静态前缀（`*` 之前）做白名单校验，
DuckDB 展开 glob 时不会逃出这个前缀，所以等价于对展开后的全部文件校验，但只做一次。

## 3. namespace 的取值逻辑

`namespace.py::resolve_namespace()` 的优先级：

1. `QUANT_RUN_NAMESPACE` 环境变量（**推荐**，shell rc 里一次 export）
2. 兜底 `anon__<git-branch>__<pid>`

**为什么不用 `~/.quant_user_alias` 文件**：共享 `$HOME` 会串。
环境变量是 shell 级别的隔离，两个终端互不影响。

**为什么兜底里带 pid**：两个同事都忘了 export，但 pid 不会一样，至少不会互相覆盖。
加 branch 是为了切分支跑实验不串数据。

## 3.5 写路径的设计（PR2）

### 3.5.1 `write_arrow` 的约束

**只接受 `pa.Table`，不接 DataFrame**：DataFrame 的 dtype 映射有一堆坑（datetime64[ns, tz] → timestamp、
object → string vs binary），让调用方显式 `pa.Table.from_pandas(df)` 一次搞定比我们猜更安全。

**只支持 `overwrite` / `append` 两种 mode**：
- `overwrite` 先清目标目录再写，目录清理是逐项 unlink（避 symlink 逃逸），不是 `shutil.rmtree(root)`
- `append` 加新文件、旧文件不动，文件名带 uuid 前缀防撞
- **没有 `upsert`**：读-merge-写的语义要跟 materializer 合并决定（当前 materializer 还有自己的 `PolarsResultStore`），PR3 一起做

**单文件写用 `.tmp` + `os.replace` 原子切换**：NFS 上半写状态暴露给别的 reader 非常容易踩坑。
带 `partition_by` 时交给 `pyarrow.dataset.write_dataset` 处理（它会写 hive 布局 `year=YYYY/part-xxxx-0.parquet`）。

### 3.5.2 为什么 `published` 直写永远 raise

发布（publish）本质上不是一次写，而是：**新数据写到暂存 → 旁路校验 → 原子切换成当前版本 → 旧版本归档**。
中间任何一步失败都要回滚。如果允许 `write_arrow("published_ds", ...)`，这条发布流程就被绕过去了。

所以 PR2 明确：
- `write_arrow` 检到 `access_mode == "published"` 直接 `ValidationError`
- `publish_from_staging` API 占位存在，但调用 raise `NotImplementedError("PR3 ...")`
- 当前需要发布的，继续走手工流程（联系 `#quant-platform`）

### 3.5.3 `_resolve_write_dir` 的实现

给一个 glob 算写入根目录的算法：按 `/` 切段，从左往右取，遇到第一个含 `*` 或 `?` 的段就停，
前面那些段拼起来就是根目录。

```
/xx/runs/mom_3d/**/*.parquet        → /xx/runs/mom_3d
/xx/factors/mom_3d/year=*/*.parquet → /xx/factors/mom_3d   （year=* 整段被截掉）
/xx/factors/mom_3d/*.parquet        → /xx/factors/mom_3d
```

**为什么不直接 `glob[:glob.index("*")]`**：那会把 `year=` 留下来，pyarrow 写 hive 分区时会在
`year=` 下面再建一层 `year=2024/`，得到 `mom_3d/year=/year=2024/...` 这种双层目录。

### 3.5.4 审计日志

`audit.py` 是 append-only JSONL，单 `_write_lock` 串行化磁盘追加。**审计失败不破坏业务路径**
（捕获异常、记 stderr，但不 raise）——审计是观测层，不能反向阻塞生产脚本。

默认只记 `write`，不记 `read`（量太大，1 天几万条）。调查问题时 `QUANT_AUDIT_READS=true` 打开。

`operator` 字段走比 `namespace` **更宽松**的 sanitize：允许 `@ + . _ -`，因为只进 JSON 不进路径，
`shw@team` 这种邮箱风格身份更有参考价值。`namespace` 则严格（只 `[A-Za-z0-9._-]`），必须能安全拼进 `open()`。

## 4. 为什么 `ParquetSource` 不直接删

兼容合同：`factor_engine` 里很多因子代码调用 `source.load_column(name)` 拿
`(timestamp, instrument)` MultiIndex Series。这个 API 契约在老代码里到处依赖。

PR1 的做法：把 `ParquetSource` 底层改成走 `data_access.get_shared_engine()`，
公开 API 字节不变，但多了一个 `load_columns([...])` 批量版本供新代码用。

**单文件容错**：`_duckdb_read_batch` 首选（一次 SQL 读所有文件）；失败降级到
`_duckdb_read_per_file`（逐文件 + 跳过坏文件）。这保留了老版本遇到坏 parquet 不全挂的行为。

PR3+ 会看实际使用情况，考虑把 `ParquetSource` 改为 `DataAccessStore` 的 thin wrapper 或整个下线。

## 5. 测试策略

| 层 | 位置 | 覆盖 |
|---|---|---|
| unit | `data_access/tests/unit/` | 单模块（namespace、retry、predicate、paths、adapters） |
| contract | `data_access/tests/contract/` | 端到端 + parity 对照（DuckDB 结果 == pandas 结果） |
| concurrency | `data_access/tests/concurrency/` | 多线程稳定性（锁定 1.1 节的选择） |
| backward-compat | `factor_layer/factor_engine/tests/test_parquet_source.py` | ParquetSource 老合同 |

**golden 对照用语义 hash，不用字节 hash**：DuckDB 可能把 tz 去掉，
可能把整数 physical type 调一下；我们只断言值集合相等（`sort_values + assert_frame_equal(check_dtype=False)`）。
这避免每次 DuckDB 小版本升级就得重生成 golden。

## 7. 已知限制 & 反模式

### 限制

- **不支持流式读取**：`read_arrow` 一次把结果拉进内存。单次查询 >100GB 结果会 OOM。
  解决：加 `time_range` / `instrument_filter` 分批；真需要流式，PR3+ 考虑加 `read_arrow_stream()`。
- **不支持写 published**：`write_arrow` 只开了 `namespaced / staging`，`published` 直写会 raise。
  要发布的，PR3 的 `publish_from_staging` 落地之前继续走手工流程。
- **不支持 upsert / sql escape**：都留到 PR3。临时读单个 parquet（未登记）仍推荐在 `datasets.yaml` 里
  临时登记一个 namespaced dataset，而不是绕开框架。
- **schema evolution**：靠 `union_by_name=true`，但缺列会被填 NULL。业务代码要自己判 NULL。

### 反模式

```python
# ❌ 每列一次调用
for col in ["close", "volume", "open"]:
    df = store.read_frame("ds", columns=[col])

# ✅ 一次拿齐
df = store.read_frame("ds", columns=["close", "volume", "open"])
```

```python
# ❌ 拿到 DataFrame 再 filter
df = store.read_frame("ds")
df = df[(df["ts"] >= "2024-01-01") & (df["ticker"] == "AAPL")]

# ✅ 下推到 DuckDB
df = store.read_frame("ds",
    time_range=("2024-01-01", None),
    instrument_filter=["AAPL"],
)
```

```python
# ❌ 多次 get_store() 期望拿到不同实例
s1 = get_store()
s2 = get_store()   # 和 s1 是同一个

# 用于测试隔离：reset_store() 强制重建
```
