## 第 4 分钟：批量多列 → MultiIndex Series

写因子时常用：

```python
cols = store.load_columns(
    "us_stocks_sip_day_aggs",
    columns=["close", "volume", "open"],
    time_range=("2024-01-01", "2024-06-30"),
    instrument_filter=["AAPL"],
)

close = cols["close"]
# close 的 index 是 MultiIndex [timestamp, instrument]
# close.name == "close"
print(close.head())
```

这一次调用底层只发一条 SQL（`SELECT close, volume, open, ...`），
比老的 `for c in cols: source.load_column(c)` 快 3~10x（列数越多差距越大）。

### 重命名输出列

```python
cols = store.load_columns(
    "us_stocks_sip_day_aggs",
    columns=["close", "volume"],
    output_names={"close": "px", "volume": "vol"},
)
# cols["px"], cols["vol"]
```

## 第 6 分钟：写自己的数据（PR2）

个人回测 / 待发布因子都走 `write_arrow`。published 数据集**永远**不能直写。

```python
import pyarrow as pa

# 个人回测结果：namespaced 数据集
tbl = pa.table({
    "timestamp": pd.date_range("2024-01-01", periods=100, freq="D"),
    "symbol": ["AAPL"] * 100,
    "pnl":    [...],
})

store.write_arrow(
    "single_asset_backtest_runs",
    tbl,
    strategy_id="mom_3d",   # params_schema 里要求
    version="v1",
    mode="overwrite",       # 或 "append"（追加新文件，不动旧的）
)
# 返回：{"rows": 100, "path": "/.../users/shw/backtests/...", "files": [...], "mode": "overwrite"}
```

带分区（staging 因子湖的典型用法）：

```python
store.write_arrow(
    "factor_lake_staging",
    tbl,
    factor_id="my_new_factor_v1",
    mode="overwrite",
    partition_by=["year"],   # 生成 year=2024/part-xxxx.parquet
)
```

写完可以直接 `read_frame` 回来校验：

```python
got = store.read_frame("single_asset_backtest_runs", strategy_id="mom_3d", version="v1")
```

**不能做的事**：

```python
# ❌ 直写 published 数据集
store.write_arrow("factor_lake", tbl, factor_id="xxx")
# raise ValidationError("数据集 'factor_lake' 是 published，不允许直写...")
```

## 第 7 分钟：合并写入 `upsert`（PR3）

增量算因子、回填时「新键覆盖旧键、旧键保留」的典型场景。`write_arrow` 的
`overwrite` 会清目录，`append` 会堆碎片还不去重——都不适合。这种场景用 `upsert`：

```python
# 当天新算了一批，合并进 staging；同 (datetime, asset) 后写覆盖先写
store.upsert(
    "factor_lake_staging", new_tbl,
    factor_id="mom_3d",
    upsert_on=["datetime", "asset"],   # 合并键
    partition_by=["year"],             # 只重写涉及的分区，不动其他年
)
```

**三种写入场景对比**：

| 你要做的 | 用什么 | 为什么 |
|---|---|---|
| 一次算完完整历史，重写整个目录 | `write_arrow(mode="overwrite")` | 最干净；旧文件全清掉 |
| 纯新增独立数据，不会和旧的撞键 | `write_arrow(mode="append")` | 不动旧文件，uuid 前缀防撞名 |
| 新数据 + 旧数据按键去重合并 | `upsert(upsert_on=[...])` | 读-merge-写，旧键保留、新键覆盖 |

`upsert` 带跨进程文件锁（父目录 `.upsert.<name>.lock`，O_EXCL 创建、5s 轮询），
同一 dataset 的并发 upsert 会被序列化。带 `partition_by` 时按分区粒度锁+合并，
不会锁全表。

**注意**：`upsert` 同样禁止写 `published` 数据集（直接 `ValidationError`）。

## 第 8 分钟：临时 SQL 分析 `sql()`（PR3）

大部分查询 `read_arrow` 能覆盖，但 GROUP BY、window、多表 JOIN 不行。
PR3 开了一个**受限**的 SQL 逃生口：

```python
# 因子值 + 对应日的收盘价 JOIN 起来看
tbl = store.sql(
    """
    SELECT f.asset, f.datetime, f.value, p.close
    FROM factor_lake f JOIN us_stocks_sip_day_aggs p
      ON p.align_time = f.datetime AND p.ticker = f.asset
    WHERE f.value > ? ORDER BY f.datetime
    """,
    read_datasets=["factor_lake", "us_stocks_sip_day_aggs"],
    read_params={"factor_lake": {"factor_id": "mom_3d"}},
    params=[0.5],
)
print(tbl.num_rows)
```

**硬规则（踩了会 raise）**：

1. 只能 SELECT；出现 `INSERT / UPDATE / DELETE / COPY / CREATE / PRAGMA /
   read_parquet / read_csv / ATTACH` 等关键字直接拒绝
2. FROM 的表名**必须**是 `read_datasets=[...]` 声明过的数据集；
   其他 dataset 没注册成 TEMP VIEW，SQL 引擎根本找不到
3. 谓词里的值用 `?` 绑定，走 DuckDB prepared statement（不要手拼 SQL 字符串）
4. 每次 `sql()` 调用都进审计日志

**什么时候不要用 `sql()`**：
- 能用 `read_arrow` 的就别用 `sql()`——`read_arrow` 走 registry 的谓词下推更快、更安全
- 跑定时任务 / 生产 pipeline：`sql()` 是 ad-hoc 分析工具，不是稳定 API

## 第 9 分钟：发布 `publish_from_staging`（PR3）

在 staging 写完 + 自测通过后，晋升到全员只读的 published：

```python
store.publish_from_staging(
    "factor_lake_staging", "factor_lake",
    factor_id="mom_3d",     # 两边 params_schema 要求一致
)
# → {"target_path": "/.../factors/mom_3d", "archive_path": ".../_archive/...",
#    "rows": 12345, "ok": true}
```

内部流程：
1. 复制 staging 到候选目录
2. 拿锁（`.publish.<name>.lock`，O_EXCL，5s 超时）
3. 把当前 published 归档到 `_archive/<timestamp>/`
4. rename 候选目录为 published（原子切换）
5. 读回校验；任何一步失败会尽力回滚

**什么情况会 raise**：
- staging 和 published 的 `time_column / instrument_column / params_schema /
  layout` 不一致 → `ValidationError`
- 锁超时（另有进程在 publish 同一个名字）→ `EngineError`
- 候选目录校验失败（行数为 0 / schema 漂移）→ 自动回滚后 raise

**回滚**：归档目录保留在 `_archive/` 下，手工 `mv` 回来即可（记得先联系 `#quant-platform`）。

## 第 10 分钟：大表流式读 `read_arrow_stream`（PR7）

`read_arrow` 一次把整张表 materialize 到内存——几百 MB 的查询没问题，
上到几 GB 就容易 OOM，尤其是因子回测批量跑、或者 ETL 扫全量日线的时候。
这时候用 `read_arrow_stream`，按 batch 拉：

```python
total_rows = 0
for batch in store.read_arrow_stream(
    "factor_lake",
    factor_id="mom_3d",
    columns=["datetime", "asset", "value"],
    time_range=("2020-01-01", "2024-12-31"),
    batch_size=100_000,    # 默认 100k 行；对齐 DuckDB vector size
):
    # 每个 batch 是一个 pyarrow.RecordBatch，可以直接转 pandas/polars
    df_chunk = batch.to_pandas()
    total_rows += len(df_chunk)
    # 处理完一批就可以丢；峰值内存只占一个 batch 的大小
print(total_rows)
```

**什么时候换回 `read_arrow`**：

- 结果行数 < 百万级、或单次结果 < 500MB：`read_arrow` 更快（没有 batch 拼装开销）
- 要 JOIN / GROUP BY：用 `sql()`，不要用 `read_arrow_stream` 自己拼

**中途 break 是安全的**：reader 对象会被 GC 自动回收，底层 cursor 随之释放。

**不要跨线程传 reader / generator**：DuckDB 的 batch reader 是单线程对象。
如果要并行处理，一个 worker 线程自己发一次 `read_arrow_stream`。

## 第 11 分钟：`scan_polars` —— Polars LazyFrame 适配（PR7）

Polars 的 lazy engine（Rust 实现）在多表 JOIN、窗口函数、复杂变换上比
「Arrow → to_pandas → 再转 polars」快得多，且支持列/谓词/分区三重下推。
复杂因子 pipeline 建议直接用 `scan_polars`：

```python
import polars as pl

lf = store.scan_polars(
    "factor_lake",
    factor_id="mom_3d",
    columns=["datetime", "asset", "value"],
    time_range=("2024-01-01", None),    # 作为 lazy filter 附加
    instrument_filter=["AAPL", "MSFT"],
)

# 继续在 LazyFrame 上搭 pipeline——直到 .collect() 都不物化
result = (
    lf.with_columns((pl.col("value") * 100).alias("value_bps"))
      .group_by("asset")
      .agg([pl.col("value_bps").mean().alias("avg_bps"),
            pl.col("value_bps").std().alias("std_bps")])
      .sort("asset")
      .collect()     # ← 到这里才真正读 parquet + 跑计算
)
print(result)
```

**和 `read_frame` 的区别**：

| 场景 | 推荐 |
|---|---|
| 简单列读 + 过滤，直接画图/落表 | `read_frame`（pandas） |
| 多步 transform / join / groupby，中间结果不想物化 | `scan_polars` |
| 结果不需要 pandas、只是下游继续算 | `scan_polars` |

**前置条件**：需要 `polars` 已安装（`pip install polars`）。没装会抛清晰的 `ImportError`。

**注意**：`scan_polars` 返回的是 LazyFrame，不走 DuckDB 引擎，也不记遥测
（Polars 自己管 I/O）。想要看 I/O 耗时用 `lf.explain()` 或 Polars 的 profile API。

## 第 12 分钟：Schema 首访自检（PR8）

PR8 起，数据集可以在 `datasets.yaml` 里声明 `schema:`，每个数据集**第一次**被读时会
跑一次 schema 对齐校验——parquet header 里列齐全、类型兼容就过，漂移就按模式处理：

```yaml
us_stocks_sip_day_aggs:
  # ... 其他字段同上 ...
  schema:
    align_time: timestamp    # 别名：匹配 DuckDB 的 TIMESTAMP / TIMESTAMPTZ / TIMESTAMP_NS
    ticker: string
    close: double            # 匹配 DOUBLE / REAL / DECIMAL
    volume: int              # 匹配 BIGINT / INTEGER / SMALLINT / TINYINT
```

**支持的类型别名**（宽松匹配，够业务用）：

| 写这个 | 匹配这些 DuckDB 类型 |
|---|---|
| `timestamp` / `datetime` | `TIMESTAMP`, `TIMESTAMP WITH TIME ZONE`, `TIMESTAMP_NS`, `TIMESTAMP_MS` |
| `date` | `DATE` |
| `int` / `int64` / `int32` | `BIGINT`, `INTEGER`, `SMALLINT`, `TINYINT`, `HUGEINT` |
| `double` / `float` / `decimal` | `DOUBLE`, `REAL`, `DECIMAL(*)`, `FLOAT` |
| `string` / `str` / `varchar` | `VARCHAR` |
| `bool` / `boolean` | `BOOLEAN` |
| 直接写 DuckDB 原生类型 | 精确匹配（`VARCHAR`, `BIGINT`, `DECIMAL(18,4)` ...） |

**三态开关**（环境变量 `QUANT_SCHEMA_CHECK`，默认 `warn`）：

```bash
export QUANT_SCHEMA_CHECK=warn      # 默认：打 WARNING 不阻塞
export QUANT_SCHEMA_CHECK=strict    # 生产推荐：漂移即 raise ValidationError
export QUANT_SCHEMA_CHECK=off       # 本地调试偶尔用：彻底跳过
```

**命中缓存**：同 dataset 进程内只校验一次。warn 模式下也只告警一次（不会刷屏）。

**触发的典型报错**（strict）：

```
ValidationError: dataset 'factor_lake' schema 校验失败:
  缺失列（声明了 registry 但 parquet 里没有）: ['some_new_col']
  类型不匹配:
    - value: 声明=int 实际=DOUBLE
  实际 parquet schema:
    - datetime: TIMESTAMP
    - asset: VARCHAR
    - value: DOUBLE
  修复方式：a) 若声明错了，改 data_access/config/datasets.yaml 的 schema 块；
           b) 若数据确实漂移了，先联系 #quant-platform，确认上游生产路径是否变更。
```

**什么时候 skip schema 声明**：
- staging / namespaced 数据集（用户自己在写，schema 还在变动）
- 多 schema 合一的数据集（比如 `massive_ticks` 同时存 trades 和 quotes），
  yaml 里单列的 schema 无法覆盖两边，就别写 schema 块。

## 第 13 分钟：审计日志在哪看

## 踩坑指南

### 我的 `time_range` 传了字符串也能工作吗？

能。底层 `predicate.compile_predicate` 会用 `TIMESTAMP` literal 绑定。
支持：`"2024-01-01"`、`"2024-01-01 05:30:00"`、`pd.Timestamp("...")`、
`datetime(...)` 对象、`None`（开区间）。

### 可以 `store.sql("SELECT ...")` 吗？

**PR3 起可以，但有限制**：只读 SELECT、FROM 的表必须先 `read_datasets=[...]` 声明、
禁用 `read_parquet / INSERT / COPY / PRAGMA` 等入口、全程走审计。详见第 8 分钟。
能用 `read_arrow` 就别用 `sql()`——路径下推在 `read_arrow` 里做得更彻底。

### 我忘了 `export QUANT_RUN_NAMESPACE` 还能写吗？

能。但 `write_arrow` 会打 warning，审计日志里 `namespace_explicit=false`，
路径被兜底成 `anon__<branch>__<pid>`。写完自己记得 export 真名重跑一遍，
否则别人在你兜底目录里捞不到数据，审计也追不到是谁干的。

### 能读单个 parquet 文件吗（不在 datasets.yaml 里）？

直接调用：不行。想这么干的常见场景是 debug，
请在 `datasets.yaml` 临时登记一个 namespaced 的 dataset。
一次性脚本可以用 `pd.read_parquet`，但别 commit 进正式代码。

### DuckDB 内存打爆怎么办？

```bash
export DUCKDB_MEMORY_LIMIT=16GB      # 默认不限，DuckDB 会用到物理内存 80%
export DUCKDB_THREADS=8              # 默认 cpu_count()
```

这两个环境变量 `engine.py` 会读。改完重启 Python 生效。
